## Decision: no URL locale routing

`packages/app` can be built as a static export (`NEXT_PUBLIC_CLICKHOUSE_BUILD`
sets `output: 'export'`). Next.js locale routing (`i18n` in `next.config`) is
incompatible with static export, so the app uses:

- `next-i18next` in Pages Router mode, config passed explicitly to
  `appWithTranslation`.
- No `i18n` section in `next.config.mjs`.
- No `serverSideTranslations`. Locale resources are bundled.
- Locale is a user preference stored in `localStorage` (`hdx-locale`), switched
  with `i18n.changeLanguage`.

`zh-CN` is the default locale. English stays fully supported and is the
fallback. Because the static HTML is rendered in the default locale, English
users see one paint of Chinese before the saved locale is applied.

If URL-based locales are required later, the static ClickStack build needs a
separate strategy first.

## Library choice

`next-i18next@16` (Pages Router subpath `next-i18next/pages`), `i18next@27`,
`react-i18next@18`.

Do not import `appWithTranslation` from the package root in this version; the
Pages Router entrypoint is explicit so the App Router entrypoints stay out of
the bundle.

## File layout

```
packages/app/
  next-i18next.config.js          # locales, namespaces, bundled resources
  public/locales/
    zh-CN/<namespace>.json        # default locale
    en/<namespace>.json           # fallback and test locale
  src/i18n/
    useLocale.ts                  # locale state, persistence, <html lang>
    LocaleInitializer.tsx         # applies the saved locale after mount
    format.ts                    # locale-aware number/date helpers
    test-i18n.ts                  # English instance for Jest
```

## Key conventions

- Semantic keys, never English sentences: `search.filters.apply`.
- Nested objects, `keySeparator: '.'`, `nsSeparator: ':'`.
- Interpolate values; never concatenate translated fragments.
- Use `<Trans>` when a sentence contains a link, code, or formatting.
- Plural forms use `count` (`_one` / `_other`); Chinese supplies `_other`.
- UI text stays sentence case in English.
- Do not translate telemetry data, SQL/PromQL, source names, attribute keys,
  dashboard/saved-search names, or SQL fragments.
- A pure helper that supplies UI text returns a translation **key** (or a small
  enum of keys); the component calls `t`. Examples: `getAvailablePresets`
  (`labelKey`), `getRequestPanelTitleKey`, `getWebhookTemplateVariables(t, …)`.
  This keeps hooks out of helpers and lets tests assert structure, not copy.

## Formatting

- `useFormatTime` is the single funnel for display dates. It receives the active
  locale and passes it to `formatDate`.
- Extend `packages/common-utils`'s `formatDate` with an optional `locale`.
- `date-fns` locales: `en` -> `enUS`, `zh-CN` -> `zhCN`.
- Number displays use the active locale via `Intl.NumberFormat`.
- Parsing-only formatters (`timeZone.ts` offset math, CSV export) stay
  `en-US`; they are not display text.

## Checks

- `yarn workspace @hyperdx/app i18n:check` verifies key parity and
  `{{placeholder}}` parity across locales.
- Unit tests run against the English resources.
- E2E builds set `NEXT_PUBLIC_DEFAULT_LOCALE=en` (see `playwright.config.ts`)
  so existing English selectors stay deterministic. Production and static
  export builds keep `zh-CN`. `tests/e2e/features/shared/locale-switch.spec.ts`
  covers switching to Chinese and persistence across reloads.
- `yarn build:clickhouse` must stay green; it is the static-export canary.

## What is intentionally not translated

These stay in English in both locales:

- SQL keywords and clauses shown as syntax (`SELECT`, `FROM`, `WHERE`,
  `ORDER BY`), and query examples in the search syntax reference.
- Column-name placeholders in source forms (`Timestamp`, `ServiceName`,
  `Body`, `ResourceAttributes`, …) — they name ClickHouse columns, not UI copy.
- Product and protocol names (`ClickHouse`, `Kubernetes`, `OpenTelemetry`,
  `Slack`, `incident.io`, `Terraform`, `UTC`).
- Telemetry data, attribute keys, source/connection names, dashboard and
  saved-search names, and webhook URL examples.
- The AI summary's locally generated prose and theme names, which are produced
  in `aiSummarize/logic.ts` from phrase templates rather than rendered copy.
- Console logs and API error payloads.

## Adding a locale

1. Add the locale code to `next-i18next.config.js`.
2. Copy every namespace from `public/locales/en`.
3. Add a label to `LOCALES` in `src/i18n/useLocale.ts`.
4. Run `i18n:check`.
